# CondoTrack — R1.6 FINAL VISUAL CLOSE
## 02_UX_RESEARCH_GUARDRAILS.md

**Scope:** UX constraints for the Reception visual-close pass.  
**Purpose:** improve visual quality without breaking operational clarity or inventing new product behavior.

## 1. Core principle

This pass is not a product rewrite. Preserve existing data, routing and working flows unless a documented R1.6 requirement explicitly corrects them.

Visual refinement must improve:
- status visibility
- recognition over recall
- scan speed
- consistency
- error prevention/recovery
- user control
- accessibility
- responsive continuity

Do not use UX heuristics as an excuse to flatten CondoTrack into generic SaaS UI.

## 2. Operational hierarchy

Reception is a fast operational role. On every screen, the user should be able to identify within seconds:
1. where they are;
2. what is happening now;
3. the most important state;
4. the next valid action;
5. how to recover/cancel/close.

Prefer one clear primary action per operational context.

## 3. State visibility

Never communicate state by color alone.

Use combinations of:
- explicit label
- icon where useful
- textual status
- position/hierarchy
- semantic color

Critical examples:
- Accesos: AUTORIZADO / VENCIDO / NO ENCONTRADO must be unmistakable before the action is taken.
- Entregas: Recibido / Avisado / Retirado must not rely only on hue.
- Incidencias: severity and workflow state are separate concepts and must be separately readable.

## 4. Recognition before recall

Keep relevant context visible when it reduces memory load:
- unit number
- person/visitor name
- event time
- current status
- associated access/pass
- incident location/context

Use progressive disclosure for secondary detail instead of hiding primary context behind multiple clicks.

## 5. Lists and list-detail behavior

For Unidades, Incidencias and Activity:
- preserve list context when detail opens;
- selected row/item must remain identifiable;
- desktop detail should use a side panel/drawer or dedicated detail region, not a giant mobile bottom sheet;
- back/close must return to the same scroll/filter state where feasible;
- headers and columns must have stronger hierarchy than body rows;
- long detail belongs behind disclosure, not in every row.

## 6. Search behavior

The global Reception search is a compact control, not a permanently exposed dashboard input.

On activation:
- expand horizontally **toward the left**;
- reorganize surrounding space smoothly rather than overlap unpredictably;
- autofocus the input;
- show the query clearly;
- present useful grouped results;
- support keyboard navigation with Up/Down;
- Enter opens the focused result;
- Escape closes and restores the compact control;
- focus returns to the trigger after close when appropriate.

Do not:
- open a full-screen search modal on desktop without need;
- trap keyboard focus incorrectly;
- leave the expanded input visually stuck;
- hide the close/escape path.

## 7. Forms and drawers

Desktop operational forms should be compact side drawers/panels with clear ownership of the action.

Requirements:
- visible title and context
- concise labels
- validation close to the field
- primary action visible without excessive scrolling
- cancel/close path
- preserve entered data if an accidental non-destructive close can reasonably be recovered
- do not use a huge mobile-style sheet on 1440 x 900

## 8. Error prevention and recovery

Before destructive or state-changing actions:
- make the object and action explicit;
- disable impossible actions with an explanation where useful;
- avoid ambiguous double-primary buttons.

After action:
- show immediate state confirmation;
- preserve a recovery path where the product supports it;
- avoid success states that obscure the next operational task.

For access verification:
- scanning/verifying does not itself equal registering an entry;
- show verified identity/state before `Registrar ingreso`.

## 9. Role and permission correctness

Reception must not be shown controls that imply authority it does not have.

### Mudanzas
Reception can:
- see an approved move
- inspect operational details
- act on the building-day workflow if already supported

Reception cannot:
- approve a move
- reject a move
- create an approval decision

### Unidades
Hide finance and non-operational property detail unless explicitly required by an existing working Reception flow.

## 10. Navigation consistency

Active desktop navigation is indicated through **charcoal/contrast**, not yellow.

Keep:
- stable destination naming
- stable icon language
- stable order where already functional
- no duplicate navigation patterns inside the same shell

Contextual rails on Home are actions/contexts, not a second global navigation system.

## 11. Profile control

The `DS` profile control must open a real dropdown containing:
- Perfil
- Cambiar perfil/rol when supported and applicable
- Cerrar sesión

The menu must:
- have keyboard focus management
- close with Escape
- close on outside click
- expose a clear focused/selected state

## 12. Accessibility

### Contrast
Meet WCAG AA for normal operational text and controls.

Pay special attention to:
- small secondary labels
- placeholder text
- glass surfaces
- dark mode borders
- disabled controls
- status text

### Focus
Every interactive element must expose a visible keyboard focus state in both themes.

### Targets
Use comfortable targets. As a working minimum:
- touch-oriented controls: ~44 x 44 px
- dense desktop controls: do not reduce below a comfortably clickable ~36-40 px target without a strong reason

### Motion
Respect `prefers-reduced-motion` per `03_MOTION_AND_SENSOR_SPEC.md`.

## 13. Responsive guardrails

Desktop 1440 x 900 is the priority review surface, but R1.6 must not regress responsive behavior.

When reducing width:
- preserve action priority;
- collapse secondary information before primary state/action;
- maintain readable hit targets;
- do not simply scale the entire desktop layout down;
- rails/panels may stack or transform, but must preserve the same information model.

## 14. Dark mode guardrails

Dark mode requires explicit tokens for:
- background
- surface
- elevated surface
- text primary
- text secondary
- border
- glass
- elevation/shadow
- hover
- focus
- statuses

Do not mechanically invert light-mode values.

Dark mode should preserve:
- hierarchy
- semantic status meaning
- readable glass
- restrained yellow accent
- distinct surface depths

## 15. Copy and density

Use concise operational Spanish.

Avoid:
- paragraphs inside operational cards
- redundant helper copy
- AI-sounding summaries
- decorative labels that do not change a decision

Prefer:
- short labels
- explicit status
- time/unit/person context
- one next action

## 16. QA checklist before declaring Reception visually closed

- Home still behaves as command center, not admin dashboard.
- Search works with mouse and keyboard and closes with Escape.
- Agenda exposes a real temporal model, not a generic event list.
- Mudanzas are shown only as approved operational events.
- Access verification and entry registration remain separate steps.
- Entregas use only the locked states and correct contextual action.
- Unidades do not expose irrelevant finance/property detail.
- Incidencias separate severity from workflow state.
- Activity is chronological and timestamped with progressive disclosure.
- Profile dropdown is real and keyboard-usable.
- Dark mode uses real tokens and preserves hierarchy.
- Responsive does not regress.
- No new visual-reference family has been introduced.

# CondoTrack — R1.6 FINAL VISUAL CLOSE
## 03_MOTION_AND_SENSOR_SPEC.md

**Status:** REQUIRED FOR R1.6  
**Principle:** motion communicates change, hierarchy and continuity. It is not ambient decoration.

## 1. Motion rules

Use motion for:
- search reveal
- navigation/context changes
- stacked/reveal cards
- contextual panels
- status changes
- access verification results
- newly arrived operational events

Do not use:
- infinite blinking
- looping glow
- floating decorative elements
- permanent breathing cards
- animation on every hover simply because it is interactive

Hover transitions may exist, but they do not satisfy the R1.6 motion requirement by themselves.

## 2. Timing system

Use these as implementation ranges, not as a request for a new animation framework:

- micro feedback: **120-160 ms**
- standard UI state: **180-240 ms**
- search expansion/reflow: **220-280 ms**
- contextual panel enter/exit: **240-320 ms**
- larger stacked reveal: **280-360 ms** total, with restrained stagger

Preferred easing:
- enter/reveal: smooth deceleration / ease-out
- exit: faster ease-in
- spatial reorganization: spring-like only if subtle and stable; no bouncy consumer-app feel

Avoid durations above ~450 ms for routine reception work.

## 3. Search reveal

Collapsed state:
- compact search trigger in the header

On activation:
1. trigger expands horizontally toward the **left**;
2. adjacent header space reorganizes smoothly;
3. text field becomes explicit and focused;
4. results surface enters after or during the final portion of the expansion;
5. keyboard focus is visible.

Close:
- Escape or explicit close reverses the spatial change;
- do not fade the search away while leaving a layout gap;
- return focus to the trigger when appropriate.

Reduced motion:
- no width animation if it causes discomfort;
- switch state nearly instantly with a short opacity transition at most.

## 4. Contextual panels

For Home rail actions and other detail drawers:
- panel should feel spatially connected to the triggering control;
- enter with subtle translate + opacity or masked reveal;
- background content should not jump;
- focus moves into the panel when it is modal/interactive;
- close restores context.

No giant desktop bottom-sheet motion.

## 5. Stacked / reveal cards

Use only where hierarchy benefits from sequence.

Pattern:
- primary card appears first;
- secondary cards can follow with **40-70 ms** restrained stagger;
- do not stagger long lists item-by-item;
- max visible staged group should remain small (roughly 3-4 meaningful elements).

## 6. Navigation motion

Active navigation uses charcoal/contrast, not yellow.

When changing destinations:
- active indicator can slide/morph subtly between items;
- labels/icons should not jump in size;
- motion should reinforce destination continuity rather than behave like a carousel.

## 7. Status transitions

Status changes should have a clear beginning and end.

Examples:
- pass checking -> AUTORIZADO
- pass checking -> VENCIDO
- pass checking -> NO ENCONTRADO
- delivery Recibido -> Avisado -> Retirado
- incident status change

Recommended pattern:
- existing status leaves with short opacity/scale reduction;
- new status enters with short opacity/scale increase;
- action controls update after or together with the state, not before;
- keep layout shift minimal.

Do not turn success/error into a giant generic green/red card.

## 8. Access-specific motion

### Checking state
May use:
- compact progress indication
- scan line/ring only while an actual check is in progress

### Authorized
- concise positive reveal
- identity and validity become primary
- `Registrar ingreso` appears/enables after verification

### Expired / Not found
- concise state change
- recovery next step remains visible
- no shaking the entire screen

## 9. Sensor de novedad

Purpose: make a newly arrived operational event noticeable without becoming noisy.

Eligible event classes:
- visita
- mudanza aprobada
- paquete/entrega
- incidencia
- other meaningful operational event already represented in the product

### Trigger behavior
When an eligible new event first becomes new/unseen:
- the relevant control/module performs **exactly 2 soft pulses**;
- pulse is a restrained yellow halo/gradient/ring using `#F5E500`;
- total attention animation should finish in roughly **1.4-1.8 s**;
- after the two pulses, stop permanently for that event state.

Then retain a static indicator such as:
- dot
- count
- thin ring
- small badge

No infinite animation.

### Implementation behavior
The novelty pulse should be tied to event novelty, not component mount.

Do not replay the pulse:
- every render
- every route return
- every hover
- every poll when the underlying event has not changed

Use the existing state/data architecture where possible. Do not invent a real-time backend for this pass.

A minimal local/mock state flag such as `isNew`, `unseen`, or an unseen count is acceptable if it fits the existing prototype architecture and does not break current mock data.

## 10. Smooth scrolling

Use smooth scrolling only where spatial continuity helps:
- navigating within a long Activity/Agenda region
- bringing an opened contextual section into view
- restoring known context

Do not force global cinematic smooth-scroll behavior over the whole app.

Respect reduced motion and browser/user expectations.

## 11. `prefers-reduced-motion`

When reduced motion is requested:
- disable novelty pulses;
- remove non-essential translate/scale motion;
- use near-instant state changes or very short opacity changes;
- avoid smooth scrolling;
- retain all state meaning with static labels/icons/indicators.

No information may depend on animation being seen.

## 12. Motion acceptance tests

R1.6 passes motion QA when:
- search visibly reorganizes the header instead of merely appearing;
- rail/context panels have a spatially coherent enter/exit;
- access result changes are visible and concise;
- at least the implemented novelty sensor demonstrates two finite pulses and then a static state;
- no infinite blink/glow exists;
- reduced-motion mode remains fully usable;
- animations do not cause layout instability or delay operational work.
